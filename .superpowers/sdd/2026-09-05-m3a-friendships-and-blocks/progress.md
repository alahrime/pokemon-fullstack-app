Ruling A9 (CORRECTS Ruling A7): the two traps need DIFFERENT fixes, and treating them the same would have introduced a real leak.
  - `pair_lo`/`pair_hi`: GRANT execute to authenticated. They are `least`/`greatest` over two uuids the caller already supplied and touch no data, so a grant discloses nothing. A policy expression is evaluated as the querying role and there is no definer wrapper to hide behind, so a grant is the only fix.
  - `blocked_between`: do NOT grant. It is `security definer`, so it answers for ANY pair while bypassing RLS — granting it to authenticated would let any signed-in user probe whether two arbitrary strangers have blocked each other, which is precisely the detectability the whole design exists to prevent. Ruling A7 said "a grant that exposes a boolean over two uuids the caller supplied" and that was WRONG: the uuids are not necessarily the caller's own. The fix is to declare Task 3's `accept_offer_blocked_guard()` as SECURITY DEFINER so the trigger runs as the owner, which already holds execute.
