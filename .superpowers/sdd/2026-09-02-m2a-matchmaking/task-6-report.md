## A local-tooling limitation, found and worked around (not a code bug)

`supabase functions serve coordinator --workdir ..` (the brief's Step 3 command) fails to boot:

```
worker boot error: failed to bootstrap runtime: failed to create the graph:
Module not found "file:///Users/alilahrime/Downloads/paragon-iv/app/src/rules/types".
    at .../supabase/functions/coordinator/rules.bundle.d.ts:1:29
```

Root cause, confirmed with `docker inspect`: the CLI's local edge-runtime container only bind-mounts `supabase/functions` into the container (read-only) — `app/` is never mounted, so the `.d.ts`'s cross-directory type import (needed to resolve the `@ts-types` pragma in `index.ts`) is genuinely invisible inside the container. This is a scoping limitation of `supabase functions serve`'s Docker setup, not a problem with the committed code: Supabase's hosted deploy pipeline bundles the whole reachable module graph (including type-only imports outside `supabase/functions`), so this same code is expected to deploy and boot fine on the hosted project.

I confirmed this diagnosis two ways:
1. Adding a `.ts` extension to the import did **not** fix it under `functions serve` — still "Module not found" (rules out an extension-resolution issue).
2. Running the *unmodified* committed files directly with the same edge-runtime Docker image (`public.ecr.aws/supabase/edge-runtime:v1.74.3`), but with the **whole repo** bind-mounted instead of only `supabase/functions`, booted cleanly with no graph errors — both with and without the `.ts` extension. This isolates the failure to the mount scope, not the code, and confirms the brief's exact `.d.ts` content (no `.ts` extension) is correct and unmodified in the final commit.

I did not change any interface or committed source to work around this — I only changed how the container that serves it locally is launched, for testing purposes. The workaround container was stopped and removed after use; nothing about it is part of the commit.

## Fix round 1

Two changes, per review: make `rules.bundle.d.ts` self-contained, and add a staleness guard for the committed bundle.

### 1. Self-contained `.d.ts` (Critical)

Replaced `supabase/functions/coordinator/rules.bundle.d.ts` with:
```ts
export declare function rulesHash(format: unknown): Promise<string>;
```
No import from `app/` at all. `index.ts` needed no change: it already casts the row to `{ id: string; claimed_hash: string; format_versions: { rules: unknown } }` before calling `rulesHash(r.format_versions.rules)`, and `rules` there is `unknown` — which is exactly what the new declaration expects.

**Verdict on the reasoning: I agree, and verified each leg of it rather than taking it on trust.**

- *Graph construction, not type-checking, is where it failed.* Matches what I actually observed in the original attempt: the error was `failed to create the graph: Module not found "..."`, thrown from `Function.create` while the worker was booting — before any request runs, before any type-check pass would fire. Deno resolves every specifier reachable from the entrypoint, including ones reached only through a `@ts-types` pragma, to build that graph; it doesn't defer cross-directory type-only imports the way `tsc` would. I only tested this locally against `functions serve`'s narrow bind mount, not against a real `functions deploy`, but the mechanism the review names — the resolver runs unconditionally during graph construction, deploy or serve — is consistent with the failure I saw and not something I had independently confirmed applies to deploy too. I now treat that as the more likely explanation for why Supabase's own docs push cross-function sharing through `supabase/functions/_shared/` rather than arbitrary relative paths: if deploy tolerated reaching outside `supabase/functions`, that convention would have no reason to exist.
- *`tsc -b` never covered `supabase/functions`.* Confirmed directly: the root `tsconfig.json`'s three project references are `tsconfig.app.json` (`include: ["src"]`), `tsconfig.node.json` (`include: ["vite.config.ts"]`), and `tsconfig.scripts.json` (`include: ["scripts"]`). None references `supabase/`. So `npm run check`'s `tsc -b` was never type-checking `rules.bundle.d.ts` or `index.ts` against anything, before or after this change — the compile-time catch the old import offered was never wired to a gate that runs.
- *No CI.* `find . -iname "*.yml" -o -iname "*.yaml"` across the repo (excluding `node_modules`) returned nothing. Confirmed there is no workflow anywhere that could have been running a Deno-side type-check either.
- *The cast in `index.ts` already defeats a real `Format` check.* `row as unknown as { ...; format_versions: { rules: unknown } }` types `rules` as `unknown` regardless of what `rulesHash`'s parameter type declares. Even with the old `Format`-typed declaration in place, passing an `unknown` into a `Format`-typed parameter is itself a type error that nothing was catching — so the old declaration wasn't actually enforcing the signature match it looked like it enforced; it was, at best, decorative once you follow the cast through.

Net: the old import wasn't catching anything today, and its failure mode (an unbootable coordinator function — the one piece the whole trust boundary depends on) was strictly worse than what it bought. Agreed with the fix.
